# CRM · Сделки — аналитический дашборд для Битрикс24

## Назначение и реализованные сценарии

Приложение — аналитический дашборд по сделкам CRM портала Битрикс24. Оно встраивается
в интерфейс портала (открывается как страница/вкладка по адресу
`https://app-40572fab2785.vibecode.bitrix24.tech` через шлюз VibeCode) и работает от лица
авторизованного пользователя — личность подставляется шлюзом в каждый запрос, поэтому
собственного логина не требуется.

Реализованные сценарии:

- **Сводка по стадиям воронки** — по каждой стадии (`stageId`) показано количество
  сделок и их сумма. Раскрываются по читаемым названиям, выигранные (`WON`) и
  проигранные (`LOSE`) стадии выделяются цветом (успех — зелёным, провал — красным,
  остальные — нейтральным), а порядок повторяет расположение стадий в канбане портала.
- **Ключевые показатели** — общая сумма открытых сделок в работе, количество
  выигранных сделок за выбранный период и средний чек по выигранным сделкам.
- **Последние сделки** — таблица из 15 последних по дате создания сделок с названием,
  суммой, стадией и ответственным. Название — ссылка на карточку сделки в портале.
  Таблица сортируется по любой колонке: клик по заголовку сортирует по ней, повторный
  клик меняет направление (Сделка, Сумма, Стадия, Ответственный, Создана). Расположена
  справа от блока «Воронка по стадиям».
- **Фильтр по периоду** — по дате создания сделки: за всё время, 30/90/180 дней,
  текущий год. Корректно пересчитывает все блоки дашборда.
- **Фильтр по воронке** — по умолчанию дашборд работает с воронкой
  «Продажи услуг (общее)» (в портале — общая воронка, `categoryId 0`), но список
  направлений («Все воронки» и конкретные категории) доступен в выпадающем списке.
  Это снимает «дубли» стадий успеха: в разных воронках свои стадии, которые в сводке
  по `stageId` подписывались бы одинаково («Успешно» × N).
- **Фильтр по стадии воронки** — выпадающий список стадий текущего среза; выбор
  конкретной стадии сужает KPI, воронку и таблицу последних сделок до сделок этой
  стадии.
- **Тёмная / светлая тема** — переключается кнопкой в шапке; по умолчанию следует
  системной настройке, выбор запоминается в браузере.
- **Переключатель «Все / Мои сделки»** — срез только по сделкам текущего
  авторизованного пользователя (по `assignedById`).

## Архитектура и запрошенные скоупы

Приложение — Node.js-сервер без внешних зависимостей (только встроенный `node:http`)
плюс статический фронтенд (`public/`). Ключевые решения:

- **Данные из реального портала.** Дашборд читает сделки подключённого портала
  Битрикс24 через REST-прокси (`BITRIX_API_BASE_URL` + `X-Api-Key`), как и положено
  приложениям платформы VibeCode. Никаких моков.
- **Портал отвечает десятками секунд — поэтому запросы к порталу делает только сервер
  в фоне**, а посетителю снимок отдаётся из памяти мгновенно. Ключ доступа никогда не
  покидает сервер (в браузер не попадает).
- **Честная агрегация.** Сделки выгружаются в фоне пагинацией по курсоверу (`>id`),
  агрегация по стадиям и периодам выполняется по полному срезу, а не по одной странице.
- **Устойчивость к сбоям.** Если свежий снимок получить не удалось, приложение отдаёт
  последние успешные данные с подписью «обновлено N минут назад». Каждая ошибка портала
  несёт свой «вид» — о ключе говорится только в двух честных случаях (`no_key`, `denied`).

Запрошенные права (скоупы): для работы приложению достаточно **чтения CRM-сделок
(скоуп `crm`)**, потому что оно только агрегирует и показывает данные и ничего не пишет
и не изменяет в портале. Личность текущего авторизованного пользователя для фильтра
«Мои сделки» приходит из заголовка шлюза платформы (`X-Vibe-User-Id`), поэтому отдельного
скоупа `user` и собственного логина с паролем не требуется. Обоснование: минимальный набор
прав снижает поверхность атаки и соответствует принципу наименьших привилегий.

## Известные ограничения

- Названия стадий берутся из живого справочника статусов портала (`/statuses`,
  сущности `DEAL_STAGE*`): стандартные стадии (Новая, в работе, Успешно, Провал и т.п.)
  и кастомные коды (`C6:5`, `C123:2`, `ANOTHER_PRODUCT` и др.) раскрываются в
  человекочитаемые имена. Если какой-то стадии нет в справочнике, используется
  резервный словарь соглашений Битрикс24; в крайнем случае показывается сам код.
- Ответственный в списке последних сделок показывается полным именем (ФИО) из
  справочника сотрудников портала; если имя не найдено — выводится ID.
- Дашборд строится на данных, собранных фоновым снимком (обновление каждые ~5 минут),
  поэтому свежесть привязана к моменту сбора, а не к моменту открытия страницы — это
  осознанный компромисс против «зависшей» страницы под нагрузкой портала.
- По умолчанию приложение выгружает и показывает сделки только выбранной воронки
  (по умолчанию «Продажи услуг (общее)», общая воронка) — это ускоряет первичную
  загрузку на больших порталах.
- Снимок строится по сделкам, созданным за последние ~3 года: это ограничивает время
  первичной сборки на порталах с большой историей. Для задачи дашборда (открытые и
  недавно выигранные сделки) горизонт достаточен; сделки старше 3 лет в статистику
  не попадают.
- Средний чек считается по выигранным сделкам за выбранный период.

## Инструкция для проверяющего

1. Откройте приложение по адресу
   `https://app-40572fab2785.vibecode.bitrix24.tech` (входить через портал Битрикс24
   не нужно — доступ даёт шлюз VibeCode).
2. Убедитесь, что видны три KPI-карточки, сводка по стадиям с количеством и суммами и
   таблица последних сделок.
3. Выберите период в выпадающем списке — показатели, воронка и таблица пересчитаются.
4. Переключите «Все сделки / Мои сделки» — срез сузится до сделок текущего
   пользователя.
5. Нажмите на название сделки — откроется её карточка в портале Битрикс24.

## Локальный запуск

```bash
npm install   # без внешних зависимостей, проходит мгновенно
npm start     # сервер на process.env.PORT || 3000
```

Переменные окружения приходят автоматически (локально — из `.env` рядом с проектом, на
сервере — из окружения деплоя): `BITRIX_API_KEY`, `BITRIX_API_BASE_URL`,
`BITRIX_PORTAL_DOMAIN`. Секреты в исходный код не зашиты и в репозиторий не попадают
(`.env` в `.gitignore`).
