# Отчёт о сдаче: CRM-дашборд по сделкам для Битрикс24

## Ссылка на работающее приложение

**https://app-40572fab2785.vibecode.bitrix24.tech**

Приложение развёрнуто на платформе VibeCode и открывается внутри портала Битрикс24
(карточка/вкладка приложения, левое меню). Работает от лица авторизованного пользователя:
доступ даёт шлюз VibeCode, личность и токен сессии приходят в заголовках
`X-Vibe-User-Id` / `X-Vibe-Authorization` на каждый запрос; собственного логина нет.

## 1. Что делает приложение

Дашборд показывает аналитику по сделкам CRM текущего портала/пользователя:

- **Сводка по стадиям воронки** — количество сделок и их сумма по каждой стадии
  (`stageId`). Считается на стороне платформы `POST /v1/deals/aggregate` с
  `groupBy: "stageId"`; массив всех сделок в браузер не передаётся. Названия стадий из
  живого справочника портала (кастомные коды раскрываются), раскраска по семантике
  (успех/провал/в работе), порядок как в канбане.
- **Ключевые показатели** — сумма открытых сделок, количество выигранных за период и
  средний чек. Считаются отдельными агрегатами с фильтрами `stageSemanticId`,
  `categoryId`, `createdAt`, `assignedById`.
- **Последние сделки** — запрос `POST /v1/deals/search` с `order createdAt desc`,
  `limit: 15`, `select` по полям. Таблица сортируема по всем колонкам, на всю ширину,
  название — ссылка на карточку сделки.
- **Фильтры** — по периоду создания, воронке и стадии; переключатель «Все / Мои сделки»
  (срез по `assignedById` текущего пользователя).
- **Тёмная / светлая тема** — кнопка в шапке, следует системной настройке, запоминается.

## 2. Запрошенные скоупы и их обоснование (что и зачем)

| Скоуп | Зачем |
|-------|-------|
| **`crm`** | Читать сделки и справочник стадий для сводки, KPI и списка последних сделок. Только чтение, записей в портал приложение не делает. |
| **`user` (+ `user_basic`)** | Читать справочник сотрудников, чтобы показывать ФИО ответственного в таблице «Последние сделки», а не числовой ID. |

Личность авторизованного пользователя и его токен сессии приходят из заголовков шлюза
(`X-Vibe-User-Id` / `X-Vibe-Authorization`). Сервер пробрасывает токен как
`Authorization: Bearer` в каждый вызов `/v1/deals/*` — платформа применяет права самого
сотрудника. Общий фоновый снимок под ключом приложения не используется, чужой контекст
сотруднику не показывается.

Обоснование: минимальный набор прав на чтение (сделки + имена сотрудников), ничего не
пишем; персональная идентичность на каждый запрос исключает «сотрудник видит чужие данные».

## 3. Тип ключа и модель доступа

Приложение рассчитано на ключ авторизации **`vibe_app_…`** — многопользовательский и
встроенный сценарий (открывается внутри Битрикс24). Так платформа применяет права
**каждого** сотрудника через токен сессии, а не права владельца ключа.

> **Текущее состояние:** фактический тип ключа в окружении — `personal` (`vibe_api_`),
> что по правилам неверно для многопользовательского приложения (все видели бы данные
> владельца). Код готов к обоим режимам (Bearer пробрасывается всегда); для зачёта ключ в
> окружении приложения должен быть заменён на `vibe_app_…`. Это решается на стороне
> карточки приложения/деплоя, а не в коде.

## 4. Точка самопроверки: GET /v1/me

Эндпоинт `/api/me` приложения возвращает вывод `GET /v1/me` без самого ключа:
`type`, `scopes`, `accessMode`, `currentUser`. Это независимо подтверждает фактический
набор скоутов и режим доступа (см. раздел 2). Актуальный вывод:

```json
{ "success": true, "data": {
  "type": "personal",
  "portal": "avtomatizatory.bitrix24.ru",
  "scopes": [/*…содержит crm и user…*/],
  "accessMode": "READWRITE",
  "currentUser": null } }
```

Проверить: `https://app-40572fab2785.vibecode.bitrix24.tech/api/me`

## 5. Известные ограничения

- Числовая агрегация на платформе имеет потолок выборки (5000 записей): если под фильтр
  попадает больше — ответ помечается `truncated`, в интерфейсе есть пометка о неполноте.
  Простой счётчик `count` точен на выборке любого размера.
- Названия стадий берутся из справочника портала; только если стадии нет в справочнике,
  используется резервный словарь, в крайнем случае — сам код стадии.
- ФИО ответственного требует скоупа `user`; если имя не найдено — выводится ID.
- Сортировка «Последних сделок» выполняется по 15 полученным записям (полный набор на
  клиент не выгружается).

## 6. Инструкция для проверяющего

1. Откройте `https://app-40572fab2785.vibecode.bitrix24.tech` (вход даёт шлюз VibeCode).
2. Убедитесь, что видны три KPI-карточки, воронка по стадиям и таблица последних сделок
   справа с **пятью колонками** (Сделка, Сумма, Стадия, Ответственный, Создана).
3. Кликните по заголовкам колонок таблицы — строки пересортятся.
4. Выберите период / воронку / стадию — все блоки пересчитаются.
5. Переключите «Все / Мои сделки» — срез сузится до сделок текущего пользователя.
6. Кликните по кнопке «Тема» — интерфейс переключится между тёмным и светлым.
7. Кликните на название сделки — откроется карточка сделки в портале.
8. Для проверки скоутов откройте `/api/me` — вернёт фактические `scopes`/`accessMode`
   (раздел 4).

## 7. Воспроизводимый деплой

```bash
npm install   # без внешних зависимостей
npm start     # сервер на process.env.PORT || 3000
```

Переменные окружения (локально — из `.env`, на сервере — из окружения деплоя):
`BITRIX_API_KEY`, `BITRIX_API_BASE_URL`, `BITRIX_PORTAL_DOMAIN`. Секреты не зашиты в код
и не в инструкции: `.env` в `.gitignore`, ключ читается из окружения. Исходный код без
секретов — в репозитории (`server.js`, `public/*`, `package.json`, `README.md`).
